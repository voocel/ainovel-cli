# ainovel-cli v1 产品演进计划

> 状态：Active Product Plan（2026-08-29）
>
> 上游约束：[`../v1-architecture-plan.md`](../v1-architecture-plan.md) 是唯一核心架构权威。本文件定义产品范围、体验与交付顺序，不重新定义领域模型、权威关系或运行协议。

## 1. 产品目标

v1 要把同一个创作内核交付成两种自然体验：

- 一句话创作：用户只给目标，系统在预设边界内持续推进至完整作品；
- 精细创作：用户可以在任何阶段查看、修改、锁定、审阅、拒绝和继续，AI 只在剩余空间内自主创作。

两种体验可以有不同入口和默认值，但必须调用同一组 Service 用例，使用同一套 Project、CreationRun、Operation、Change 与完成契约。产品层不得通过增加“模式专用状态机”解决体验问题。

## 2. 文档边界

活跃文档只有两层：

1. 核心层：`docs/v1-architecture-plan.md`，保存长期稳定的目标、领域边界、不变量、依赖方向和架构决策；
2. 产品层：`docs/product/`，保存用户旅程、功能范围、交互、交付阶段与真实验收。

产品需求默认在既有扩展点内实现。只有需求证明现有核心不变量彼此冲突，或无法表达必要的权威/生命周期语义时，才允许提出架构变更；“实现不方便”不是修改核心的理由。

专题文档采用 `v1-product-<主题>.md`。当前只规划五个承重方向：

- [创作工作台](v1-product-creation-workbench.md)：连续创作、审阅、控制强度与用户干预；
- [长篇质量与上下文](v1-product-longform-quality.md)：分层记忆、相关事实、Context Builder 与审阅质量；
- [创作资产与个性化](v1-product-creative-assets.md)：Project Overlay、Creator Profile 与 Novel Pack 的用户体验；
- [作品库、导入与交付](v1-product-project-library-delivery.md)：作品管理、外部编辑、导入和 TXT/EPUB；
- [模型配置、运行与运维](v1-product-runtime-operations.md)：Provider、模型、进度、用量、诊断、Headless 与发布。

全局 `P0/P1/P2` 只在本文件维护；专题文档只表达方向内的能力层次，避免形成第二份路线图。

专题之间按以下边界协作：

| 方向 | 负责 | 不负责 |
|---|---|---|
| 创作工作台 | 创作动作、控制和内容决策的交互 | Provider、费用和存储运维 |
| 长篇质量 | Derived 记忆、上下文选择和审阅质量 | 页面状态与正式故事权威 |
| 创作资产 | 可复用规则、风格、样本和 Pack 体验 | 正文导入与作品发布 |
| 作品库与交付 | Project 查找、外部输入和读者成品 | 模型调用和任务调度 |
| 运行与运维 | 配置、执行健康、用量、诊断和部署 | 文学决策与内容修改 |

专题文档描述“用户需要什么”和“如何使用现有 Service/扩展点交付”，不得复制核心模型。短功能直接记录在本文件，不为每个功能创建 RFC。

## 3. 当前完成度

### 已形成稳定内核

- Project Revision 是故事事实的唯一权威；
- Proposal → ChangeSet 是正式修改的唯一通道；
- Ownership、Approval 与 Intent 保护用户控制边界；
- Operation、Workspace、Outcome 支持持久化任务、恢复与可审计产出；
- CreationRun 与 Coordinator 支持滚动规划、写章、审阅、重写和完成判断；
- Quick 与精细入口使用同一内核；
- Prompt、Pack、Creator Profile 与 Project Overlay 已有冻结和组合边界。

自动化测试已经证明小型故事的协议闭环，但这不等于真实模型质量或完整产品已经验收。

### 尚未成为完整产品

- 工作台已交付三栏布局、事件级活动流、正文逐字预览、卷/弧折叠、运行控制
  （暂停/取消/目标调整/统一续跑）、错误诊断下钻与鼠标热区（M1–M3，见
  v1-product-workbench-page.md），但仍缺章节编辑、审阅与冲突面板等精细控制层；
- Project JSONC 投影不是面向读者的 TXT/EPUB 成品导出；
- 缺少完整配置引导、模型用量/费用展示、诊断与发布体验；
- Creator Profile 的自动 scope、候选 reject 和样本检索尚未完成；
- URL Pack 安装尚未要求预期 digest；
- Workspace 清理与 Derived 淘汰尚未实现；
- 写作上下文仍装配全部 Plan/Canon，尚未具备几十章以上的有界摘要与相关事实检索；
- 用户创作要求（Directive）、正文作者标记、实体 ID 与 Host 记录的依赖边尚未实现，结构影响分析只有骨架，TUI 尚未暴露锁定、规则与审批等控制面（核心 D33–D36）。

## 4. 产品交付顺序

### P0：形成可真实使用的最小产品

前置：先落核心 D33–D35（Directive、正文作者标记、实体 ID 与依赖边），再做真实 5–8 章实证；否则实证数据采在错误的输入上，长篇上下文预算与要求满足率都无法度量。

1. 修通并验收全部已声明 CLI 入口，补齐 CreationRun 用户级控制；
2. 用真实 provider 完成一部 5–8 章小型作品，覆盖自动、等待确认、拒绝重写、崩溃恢复和最终完成；
3. 提供面向用户的正文查看及 TXT 导出；
4. 提供最小配置引导、运行进度、错误诊断和模型用量记录；
5. 把上述流程做成无需理解内部 ID、Proposal 或 Operation 术语的可用入口。

P0 出口：新用户可以从一句话得到并导出一部小型完整作品；精细用户可以在同一作品中修改方向、审阅章节并继续创作；失败后可以理解原因并恢复。

### P1：证明长篇与个性化能力

1. 建立章节/弧/卷摘要、伏笔索引、角色状态与相关事实检索；
2. 为 Context Builder 增加显式预算和可观测来源，避免全量 Plan/Canon 无限增长；
3. 完成 Creator Profile 自动作用域、候选拒绝、正反例检索与跨书验证；
4. 用 v1 自产作品验证影响分析召回率、跨章连续性和审阅重写收益；
5. 使用真实 provider usage 验证 Stable Prefix 的缓存收益；
6. 对目标数据规模执行 Canon/Plan 查询、上下文构建和启动性能基准。

P1 出口：至少一部长于小型验证故事的作品能够持续创作，且上下文规模、事实召回、成本和质量都有可检查证据。

### P2：补齐交付与生态

1. EPUB 等成品格式、作品归档和发布流程；
2. 完整创作工作台与更自然的实时干预体验；
3. Workspace 生命周期、Derived 淘汰、备份和迁移；
4. Pack URL 完整性、依赖和版本体验；
5. 根据真实需求决定是否设计 Capability Extension，不预建插件框架。

P2 出口：v1 具备替代 v0 的产品能力，并完成支持平台上的安装、升级、恢复和发布验收。

## 5. v0 能力处理原则

v0 只用于列产品能力，不作为 v1 的代码、数据或架构依赖。每项能力只做三种决定：

- 保留：用户仍需要，但在 v1 内核上重新实现；
- 替代：由 v1 的统一能力覆盖，不迁移旧机制；
- 放弃：价值不足或会破坏 v1 边界，明确不做。

优先保留的是完整创作、模型配置、进度与恢复、用户干预、成品导出、用量诊断和可用交互。v0 的并行模式、临时状态和绕过统一变更协议的补丁不得迁移。

## 6. 产品层扩展纪律

新增能力必须先回答：

1. 它读取哪一个权威 Revision？
2. 它的中间状态属于 Workspace、Runtime 还是 Derived？
3. 它若改变正式内容，如何形成 Proposal 并经过 Change Engine？
4. 它若属于整书连续创作，如何归属 CreationRun？
5. 它如何通过 Service 暴露给 CLI、TUI 或未来 Web，而不让 entry 直连 Store？
6. 它怎样证明 Quick 与精细体验仍共用内核？

能用现有答案表达，就在产品层扩展；无法表达时才提交带具体冲突证据的架构决策。

## 7. 发布验收

v1 只有同时满足以下条件，才可称为可替代 v0 的完整产品：

1. 一句话模式使用真实模型稳定完成并导出作品；
2. 精细模式可以在不中断作品历史的前提下修改、审批、拒绝、重写和继续；
3. 进程失败、模型失败、审批等待和 Revision 冲突均有可恢复路径；
4. 长篇上下文有明确预算和真实作品证据；
5. TUI/CLI 不要求普通用户理解内部协议标识；
6. 配置、用量、诊断、备份和成品交付达到日常使用要求；
7. 全部正式写入、运行归属和依赖方向继续满足核心架构测试；
8. 用户创作要求场景（S11–S13）用真实模型通过，且每条要求的核验结果可查（核心 §0.4）。

在这些条件完成前，项目状态统一表述为：**v1 核心协议与本地闭环已完成，产品化和真实长篇验收进行中。**
