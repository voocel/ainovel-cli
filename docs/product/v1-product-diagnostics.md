# v1 运行观测与问题诊断实施方案

> 状态：首版已实现，验证记录见文末（2026-09-12）
>
> 归属：[模型配置、运行与运维](v1-product-runtime-operations.md) 的实施细化，不新增产品方向或独立优先级体系。
>
> 约束：[核心架构](../v1-architecture-plan.md) 是唯一权威。本功能解释运行事实，不决定授权、提交、任务生命周期、恢复或作品完成状态。

## 1. 目的与交付结果

让系统运行中的问题能够被发现、定位和比较，让用户反馈尽量一次提供足够信息。

两条闭环：

- 系统优化：运行事实 → 异常模式与证据 → 定位需要改进的环节 → 修改后在同口径下验证。
- 用户反馈：用户描述期望与实际表现 → 本地诊断 → 导出分享报告 → 维护者定位或提出明确的补充信息请求。

第一版交付四项能力：状态解释、问题与证据、基础统计、可分享报告。不把“没有检出异常”表述为“系统没有问题”，也不承诺诊断包能独立重现模型与外部服务的所有行为。

## 2. 现有事实与实际缺口

| 来源 | 已有能力 | 使用限制 |
|---|---|---|
| CreationRun | 状态、目标、策略、创建/更新时间、事件、完成版本 | 更新时间不等于最近有效创作进展；用户等待属于正常状态 |
| Operation | 运行归属、attempt、执行器与配置摘要、状态、租约、错误 | 当前记录不等于每次尝试的完整历史；原始错误可能包含私有内容 |
| OperationEvent | 任务内序号、attempt、幂等键、事件时间、持久化消息 | 当前查询会整读 payload，不能成为长篇诊断摘要的默认路径 |
| ExecutionProfile | 冻结的配置身份、Prompt/工具身份及内容 | 默认只取必要身份；不含模型配置，不能把当前配置冒充历史执行配置 |
| agent.run_started | 每次尝试实际使用的角色、Provider、模型、生效思考强度与模型配置摘要 | 语义合规检查不经过它，其模型见对应用量事件；分享报告不导出载荷 |
| agent.run_ended | 结束摘要、TotalUsage、错误 | 非正常退出可能没有记录；恢复后累计值的口径需验证，不能直接跨 attempt 相加 |
| agent.message_committed | 已提交消息及工具结果，可定位自纠中的工具错误 | 消息含正文/Prompt等私有内容，只有本地定向下钻才读取 |
| activity.Hub | 当前进程中有界的实时反馈 | 重启会消失，不作为历史报告依据；不能覆盖持久化事实 |
| 当前 TUI `d` | 展示 Run、任务错误、工具报错和部分事件 | 报告在界面内拼装，遍历整轮任务和消息，缺少结构化发现及分享投影 |

现有 `FailureCode` 目前只包含影响执行语义的 `result_unknown`。诊断中的 `timeout`、`rate_limit` 等分类属于观测信息，不往该字段塞统计用途的枚举。

## 3. 边界与架构

只新增一个应用包 `internal/app/diag`。建议按职责拆为少量文件：

```text
app/diag/
  query.go       读取范围、快照边界、覆盖情况
  report.go      报告、问题、统计、证据引用
  rules.go       确定性判断与启发式判断
  share.go       分享白名单投影、别名化、导出
```

调用关系：

```text
已有任务、运行和事件记录 → 必要的只读存储查询
                                      ↓
                              app/diag
                               ↙           ↘
                         TUI 诊断页     Headless / 文件导出
```

- `bootstrap` 装配查询；入口不接触 Store，不自己拼装诊断结论。
- 首版允许 `app/diag → infra/store、domain/model`；只读 SQL 留在 Store。报告类型不进入 `domain/model`。
- 实施时在 `archtest` 登记上述依赖及入口/装配依赖；不新增内核到诊断包的引用。
- 规则先写普通纯函数：输入事实和分析时间，输出问题列表。同一输入和规则版本产生相同结论。
- 规则可定位到现有任务/事件；不另存一套“真实运行状态”，不创建“诊断任务”或诊断状态机。
- 报告不执行恢复。后续若加入操作按钮，仍调用原用例，由原用例重新校验当前前提；报告建议不是执行授权。
- 不创建通用规则注册中心、插件协议、观测总线或跨产品诊断框架。

## 4. 最小报告契约

`Inspect(ctx, Request) → Report` 是 TUI 和 CLI 的共同用例；`ExportShare(ctx, Request, path)` 采集并导出同一次报告的分享投影。

请求范围：

- `ProjectID`：作品；未指定 Run 时明确解析到最近一轮，并在结果中返回实际 Run。
- 可选 `RunID`：指定历史运行。
- 可选 `OperationID`：定位运行内某任务，必须校验归属。
- 本地事件详情使用游标，不能以多个“可选全量”参数绕过范围限制。分享保留作品/运行/任务范围，但不沿用本地页码，按异常选取上下文。
- 只查环境、不依赖作品数据库的入口放在后续阶段，支持配置失败等尚未形成 Run 的情况。

报告由五部分构成：

| 部分 | 必要内容 |
|---|---|
| Header | 报告格式版本、规则版本、程序构建版本、采集时间、实际范围、数据边界 |
| Summary | 已存在的运行状态、当前任务、最近持久化活动/内容提交时间，分别标记来源 |
| Findings | 稳定规则码、严重程度、确定性、影响对象、证据引用、解释与建议 |
| Metrics | 任务状态计数、attempt 数、失败/重试计数、耗时、已记录用量及口径 |
| Coverage | 哪些来源可用、缺失、截断或读取失败；统计覆盖范围与未评估项目 |

每条 Finding 的形式：

```text
code: execution.result_unknown
severity: warning
certainty: confirmed
subject: 某个 Operation / attempt
observed: 持久化失败码为 result_unknown
evidence: 对应状态与事件序号
suggestion: 查看外部任务与恢复信息，不能据此判断外部副作用未发生
```

`severity` 只表达影响；`certainty` 区分确认事实与启发式怀疑，不能用高严重程度暗示已确认根因。解释和建议采用程序维护的模板；本地原始错误独立展示，不混入可分享的说明字段。

缺失的数值使用“未记录/覆盖不全”，不填零。零表示有完整依据确认没有发生。

## 5. 首版规则与统计口径

首版优先交付可以由已有事实支持的判断：

| 场景 | 报告方式 | 不作出的结论 |
|---|---|---|
| 等待审批、主动暂停 | 正常状态与已有等待原因 | 不算故障或停滞 |
| 任务最终失败 | 确认失败事实、错误位置和上下文 | 不从任意错误字符串推断唯一根因 |
| 外部结果未知 | 确认未知状态，提示核对外部结果与恢复记录 | 不建议直接重复提交外部任务 |
| running 且租约已过期 | 确认租约过期这一事实，标采集时间 | 不等同于进程已死、外部任务已停或必定可重试 |
| 同类失败反复出现 | 给出观察窗口内次数，标为重复失败信号 | 不直接认定模型死循环；unknown 分类不聚为同一根因 |
| 成功任务中出现工具错误 | 单独统计自纠经历，与最终失败分开 | 不把已自纠的任务归为失败任务 |
| 记录读取失败、缺少结束摘要 | 明示覆盖缺口 | 不输出“未发现异常”的完整健康结论 |

“长时间无进展”先展示最后持久化事件时间、最后内容提交时间及当前状态，不在首版靠一个固定秒数触发故障结论。后续必须结合执行器类型、有效租约/外部状态、历史耗时和观测覆盖再增加启发式规则。

统计口径必须固定并随报告版本保留：

- attempt 数、模型请求重试、工具调用失败、章节重写是不同指标，不合并成一个“重试率”。
- 耗时区分排队、执行、等待用户及整轮墙钟时间；缺少边界事件时，不把 `UpdatedAt - CreatedAt` 称为执行耗时。
- Token 的单位必须注明是请求增量、消息记录值还是 attempt 结束累计值。恢复消息不重复计费；不能把消息 usage 与结束累计值再次求和。
- 首版先验证 agentcore 的恢复/TotalUsage 行为，再选择一个去重后的统计来源；无法证明口径的历史记录只展示原记录及覆盖说明，不给出误导性整轮总量。
- 实际模型与思考强度来自每次尝试的 `agent.run_started`；缓存命中或请求延迟未记录时留缺口，不能从当前模型配置或输出字数反推历史值。
- 首版不估算费用。价格版本、计费维度和实际模型身份明确后另行接入。
- 优化前后对比需考虑工作量、执行器/模型、配置是否相同及样本数。首版提供可比较数据，不做跨作品文学质量排行榜或自动根因归因。

## 6. 长篇性能与一致性

诊断不能成为新的全量读取入口。

1. 默认摘要仅读取运行/任务元数据及必要事件元数据；不调用 `Project()` 加载全书，不默认解析所有 `agent.message_committed`。
2. 统计在数据库侧按所选 Run 聚合；界面任务明细采用游标分页，起始页 50 条。历史事件按任务序号分页，每页 100 条。数值是内部交互预算，不是业务上限。
3. 仅在用户选择一个任务后定向读取该任务的错误与消息详情；同一页面更新不重复解析未变化的消息范围。旧记录若只能从消息提取工具问题，明确标“尚未展开分析”，不能声称全轮工具错误为零。
4. 读取元数据时使用短只读事务，固定采集时刻、状态和各事件流截止序号。事务外的重载荷查询必须限制在已捕获的边界内；并发出现的新事件归入下一次报告。
5. Run 与不同 Operation 事件序号不能组成全局因果顺序。展示时间仅辅助理解，保留每条流内部顺序；时间相同或时钟变化时不得伪造精确先后。
6. TUI 打开时采集、按 `r` 刷新；一次只允许一个采集请求。诊断不跟随每个 token 重算。
7. 分享报告导出聚合统计、最多 200 个任务上下文及 200 条选定证据事件。任务按异常、运行中/重试、最近更新优先选择；为选中且有事件的任务分配尾部窗口，保留每条流的边界事件。超过预算时明确列出被省略的问题证据和条数，不能把截断窗口称为完整历史，也不把任务尾部窗口称为全历史按时间排序的最新事件。
8. 缺少核心范围/对象、数据库不可读或不支持的关键记录格式时明确返回错误。局部明细不可用时允许报告标为不完整，并展示失败来源；已生成的部分内容不伪装完整成功。

覆盖与性能预算要通过 500／1000 章、长消息、多个 attempt 的实测确认；不以固定机器上的毫秒阈值编写易波动的单元测试。

## 7. 分享报告与用户反馈

### 7.1 本地详情与分享数据分离

本地诊断可以按需展示原始错误与相关事件，页面明确标注“含本地详情，请使用分享导出”。

分享导出使用独立、封闭的 `ShareReport` 类型，通过字段白名单新建对象，禁止直接序列化 Local Report、Operation 或任意事件 payload。不能采用“先打包所有数据，再用正则删密钥”的流程。

| 信息 | 默认分享策略 |
|---|---|
| 程序版本、平台、数据库 schema 版本、报告/规则版本 | 经过类型校验后保留；启动时未知的版本明确 unknown |
| 状态、内置任务/工具种类、错误分类、计数、耗时 | 保留已验证的枚举/数值；未知种类保留 unknown 标记 |
| Project/Run/Operation/attempt 关联 | 在本次报告内别名化，例如 book-1/run-1/task-3；原始 ID 可能含书名，不直接导出 |
| 配置/Prompt/输入摘要 | 必要时用本包内别名表达“同一/不同配置”；不导出原始文本摘要来做可猜测的内容指纹 |
| 实际 Provider/模型 | 仅分享已记录且列入公开标识白名单的名称；自定义名称别名化。历史实际模型来自 `agent.run_started` 与用量事件，当前配置不当作历史实际模型 |
| 时间与事件序号 | 分享相对采集时刻的时间差、任务内序号，保留耗时与关联 |
| 正文、思考、Prompt、素材、工具参数/结果、原始错误、URL/路径、密钥 | 不进入分享对象 |
| 用户的现象描述、复现步骤、期望结果 | 由用户另行填写；不自动加入诊断包或作“已脱敏”的承诺 |

别名映射只在生成过程内存中存在，不附入包内；不收集稳定设备标识，不自动上传。

新版本或未知字段默认不分享，并记录省略数量。白名单转换、类型校验或泄漏回归检查发现问题时拒绝发布文件，保留本地错误提示。敏感数据检测是第二道检查，不能替代封闭字段投影。

### 7.2 导出形式

首版只输出一个 UTF-8 JSON 文件，例如 `diagnostics.json`，同时满足可读和机器分析需要。暂不输出 ZIP、整库、日志目录或会话附件，也不同时维护 Markdown/HTML 等多个报告格式。

- 显式点击/命令才导出，不上传，不自动发 issue。
- 保存前提示默认包含/排除的信息类别；此提示用于知情，不增加重复确认流程。
- 文件先在目标目录写入临时文件，全部转换和校验通过后再发布；默认不覆盖已有文件。
- 分享投影应剥离未知字段并保留 coverage；源数据读取失败属于明确的局部/整体错误，不能以“已脱敏”掩盖。

推荐用户反馈模板仅四项：期望行为、实际现象、复现步骤/大致时间、诊断文件。需要内容才能复现时，再单独说明所需片段与原因。

## 8. TUI 与 Headless

工作台通过 `/diag` 或点击创作现场的报错行进入诊断，不增加常驻分栏，也不自动弹出大量告警。诊断页沿用已有配色和滚动方式：

```text
运行诊断                         [r 刷新] [e 分享导出]
────────────────────────────────────────────────────
当前：等待你确认稿件 · 这不是运行故障
范围：本轮运行 / 截至本次采集       覆盖：部分明细未读取

值得关注
  工具调用曾失败 3 次，任务最终成功
  → 查看任务及相关事件

运行统计
  任务 12 · 最终失败 0 · 2 个任务发生多次尝试
  已记录用量 …                    覆盖说明 …

任务列表 → 某次尝试 → 相关事件 / 本地错误详情
────────────────────────────────────────────────────
Enter 查看 · Esc 返回；原始详情不用于直接分享
```

本地详情按需展开；分享导出与成品导出是不同页面语境下的 `e`。刷新和导出失败必须显示，不影响正在进行的创作。

Headless 规划：

```sh
ainovel-cli --headless diag --project book-1
ainovel-cli --headless diag --project book-1 --run run-id
ainovel-cli --headless diag --project book-1 --operation operation-id
ainovel-cli --headless diag export --project book-1 --file ./diagnostics.json
```

普通 `diag` 输出结构化本地摘要，导出调用分享投影；两者明确标识可分享性。参数错误、收集/导出失败返回非零；“发现问题”本身不等于命令执行失败。需要 CI 判定健康状态的额外开关后续再设计，首版沿用既有 CLI 错误约定。

## 9. 观测补齐原则

在首版报告暴露的数据缺口基础上，只补充支持明确问题所需的观测：

- 请求/尝试的实际执行器与模型身份、开始/结束、结果类别、用量来源及去重身份。
- 工具调用类型、结果分类、次数与耗时，不持久化第二份工具参数和正文。
- 恢复/重试与原 attempt 的关联，沿用现有 Operation 与 attempt 标识。

先评估现有事件是否已能表达，必要时增加紧凑的版本化观测事件。事件解码在边界校验，诊断包不直接依赖 agentcore 的私有状态；不新增无用途的全局 Trace ID，不把每个 token 落库。

保持原恢复记录的可靠性要求，不为采样或性能删减恢复所必需的消息。新增的非权威观测缺失应可见，但不得自行改变提交、任务成功/失败或恢复语义；若需求确实触及这些契约，先记录架构决策。

## 10. 实施顺序与验收

本节是该能力内部的先后关系，不新增全局 P0/P1 分类。

### 第一段：共同报告与事实口径

- 固定 Report、Finding、Coverage 和规则版本；验证现有事件/usage 的恢复口径。
- 增加有界的元数据、统计和明细查询，迁出 TUI 的诊断拼装逻辑。
- 交付首版状态解释、确定事实、重复信号和基础统计；未知部分如实展示。
- TUI `d` 和 Headless 使用同一用例，保留原始错误的本地下钻能力。

验收：正常等待不报故障；成功自纠与最终失败分开；租约过期、外部结果未知、缺少结束记录和并发刷新都有正确解释；TUI/CLI 对同一输入结论一致。

### 第二段：用户反馈闭环

- 实现 ShareReport 白名单、报告内别名化、原子导出与反馈模板。
- 覆盖没有 Run 的环境诊断；数据库打不开时仍能输出明确受限的环境信息，不伪造运行报告。
- 诊断入口使用最小只读装配，不要求模型连通或启动执行器。

验收：在正文、密钥、思考、错误、工具名、自定义模型名、路径、ID 和事件未知字段中注入敏感哨兵，分享结果不得出现；同一份包能保留任务关联；同名文件、磁盘失败和取消不发布半成品。

### 第三段：依据真实报告补齐观测与优化

- 为首两段已暴露且影响定位的缺口增加必要观测，验证恢复后不重复计数。
- 用真实失败案例和改动前后同口径报告验证收益，再增加重复失败、延迟等分析。
- 费用估算、文学质量体检、长期聚合面板与远程收集不列入本轮。

共同验收：

1. 一个正常完成案例、一个正常等待案例、一个失败后恢复案例、一个外部结果未知案例、一个启动失败案例。
2. 旧事件、未知可选字段、损坏必需字段、缺失摘要和部分查询失败均有覆盖说明或明确错误。
3. 500／1000 章与大消息历史下，默认摘要不加载全部正文/消息，查询与渲染可取消、分页有界。
4. 采集和导出不修改作品版本、任务状态、租约、审批结果或业务事件；规则仅报告问题。
5. 测试聚焦误报、计数口径、信息泄漏、并发边界和真实查询开销；真实模型/故障案例验证另行进行。

首轮完成标志不是“规则数量很多”，而是：用户能说明自己卡在哪，我们能拿到足够的无正文证据，并能解释哪些原因已经确认、哪些仍需进一步调查。

## 11. 首版实现与实际覆盖

- `internal/app/diag` 统一采集、规则、局部用量解释及封闭分享投影；`bootstrap` 只负责装配。
- Headless `diag` 在配置解析和执行器装配之前进入，只读打开已有数据库，不建库、不迁移、不恢复任务。无作品范围可输出受限环境报告；数据库不可用时本地错误写入 stderr，分享 JSON 的 `database_issue` 保留缺失、权限、损坏、不支持 schema 等类别；作品范围查询仍失败。
- TUI `d` 打开诊断，`j/k` 选任务、Enter/点击下钻，`n` 下一页、`g` 首页、`r` 刷新、`e` 分享。离开页面取消采集；过期回执不更新新页面。
- 每次分页独立采集并标出实际范围与时间；`statistics` 覆盖整个所选范围，任务明细最多 50 条。最后一页仍须考虑此前省略的记录，不能因没有下一页而标为完整。摘要事件最多 200 条且不读取载荷；单任务事件每页 100 条、每条载荷最多 64 KiB，TUI 每条展示前 2 KiB 并明确提示。
- 已验证 agentcore v1.8.3 恢复消息不会重新累加 usage；当前只展示已读取结束事件的 attempt 增量，未汇总全轮用量。工具错误也只分析当前事件页，成功自纠与最终失败分开。
- 分享重新采集请求范围，忽略本地页码，按异常优先选取最多 200 个任务及其尾部事件。任务状态、类型、执行器和配置关联与证据一起导出；运行范围只解码选中结束摘要的用量，不读取消息正文；明确指定单个任务时，在有界窗口内提取工具错误。报告内 ID、执行器与配置关联均别名化，原始载荷和自由文本不进入文件。原子发布且默认拒绝覆盖。

当前限制明确呈现在 coverage：未检查模型连通性和配置内容、未采集实际历史模型或内容提交时间、未汇总全轮工具错误与用量。环境报告提供构建版本、平台和数据库打开失败类别，不将其视作完整启动故障定位；无法确定的打开错误仍标 `open_failed`。任意错误字符串不归类成同一根因；重复信号目前只针对有明确语义的 `result_unknown`。

首版使用任务当前快照与事件边界作为问题证据；摘要按任务优先级分配尾部窗口，不对全部事件按时间排序。最近事件时间来自各流末条记录的时间，不能视作跨流因果顺序。超出采集预算的任务快照与事件注明缺口，不扫描消息载荷来推断根因。

验证包括：正常等待/终态、当前 attempt 缺失摘要、隐藏在下一页的异常、历史任务归属、成功任务工具错误、只读与取消、未知/损坏用量、敏感哨兵和不覆盖发布。新增末页覆盖、位于第 205 条的失败任务分享上下文、启动失败类别与事件到任务的关联回归。

本轮全项目 `go test ./...`、`go vet ./...`、诊断相关应用/存储/入口的 `-race` 检查及格式检查通过。

长历史基准使用 500／1000 任务，每任务 200 条约 2 KiB 事件、3 次 attempt。优化前约 997／1579 ms，改为按序号读取尾部窗口后约 113／450 ms，分配约 399／387 KB；20 万事件的分享采集约 266 ms、709 KB。上述均是本机单次基准，有缓存差异，不作为固定时限或任意历史规模的承诺。查询仍需聚合所选范围的元数据，不能称作常数成本。真实模型故障与用户反馈案例仍需后续验证。
